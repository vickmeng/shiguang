# rail-code-review

对圈定的代码做六维度有序评审，输出量化评分与可执行的问题清单：每条问题带严重度、`file:line` 证据和改进方向。

## 输入

用户输入（command 注入的 `User input`），必须包含评审范围；未包含时按流程第 1 步处理。

## 流程

### 1. 圈定范围（强制）

用户未给范围时，必须立即向用户询问，不得自行猜测或默认全仓扫描。
范围确认后以只读方式收集范围内的代码与变更。

### 2. 加载项目规范

逐条加载规范依据，缺失则跳过，不臆造规范：

1. 项目规范约定（如 `AGENTS.md`）
2. `.rail/schemas/test-quality.md` — 测试维度的判定标准

若规范依据之间存在冲突，向用户汇报冲突点并中断评审，待用户裁决后再继续。

规范基准优先级：**项目规范文档 > 通用最佳实践 > 老代码惯例**。

老代码**可以**作为参照阅读——它有助于理解项目惯例和上下文；但必须清醒认识：老代码可能本身不合规，**规范文档才是最高准绳**。

- 被评审代码与某段老代码同样违反规范 → 照常报告，并降级为 🔵 建议附带注明参照的老代码 `file:line` 存在同类问题（不展开评审范围外代码、不影响评分）。
- 规范未覆盖的领域 → 可以通用最佳实践或老代码惯例作为**弱参考**，但必须标注“非项目规范”，且不得据此给出“合规”结论，只能给建议级意见。

### 3. 多维度评审

1. **规范符合性** — 以规范文档为最高准绳，老代码可作参照但不可作为合规依据；项目规范是否被遵守
2. **设计模式** — 对照 SOLID、DRY、KISS、YAGNI、迪米特法则等基本原则，评审抽象合理性、模块边界、重复代码、耦合度、是否过度设计或设计不足
3. **完成度** — 死代码、TODO/FIXME、未处理边界条件、未处理的异常分支
4. **测试覆盖** — 对照 test-quality.md：值得测试的行为是否有对应测试
5. **安全与健壮性** — 注入风险、空值/越界处理、错误处理、资源泄漏

每条问题必须附 `file:line` 证据，基于实际读到的代码，无证据不报告；不确定的问题降级为「建议」并注明。

**严重度归类（固定，不可临场调整）：**

- 🔴 严重 — 违反项目规范文档（如 `AGENTS.md`）的约定；安全漏洞；导致功能错误的缺陷
- 🟡 警告 — 违反通用最佳实践/设计原则；缺少应有测试；未处理边界条件；死代码、TODO/FIXME
- 🔵 建议 — 弱参考意见；不确定的问题；老代码同类问题；风格命名等轻微改进

违反规范文档一律判 🔴，不因「与现有代码一致」而降级。

### 4. 加权评分（百分制，权重固定）

| 维度 | 权重 |
|---|---|
| 规范符合性 | 30 |
| 设计模式 | 30 |
| 完成度 | 20 |
| 测试覆盖 | 10 |
| 安全与健壮性 | 10 |

计分：每个维度从 100 分起扣，严重 −40、警告 −15、建议 −5，扣完为止（最低 0 分）。
总分 = Σ（维度得分 × 权重）÷ 100。

权重与扣分值固定，不可临场调整。

### 5. 展示

1. **评分表** — 各维度得分、加权得分与总分（百分制）+ 一句话总评
2. **问题清单** — 按严重度分级（🔴 严重 / 🟡 警告 / 🔵 建议），每条含维度、`file:line`、问题描述、改进方向
3. **改进优先级** — 严重 > 警告 > 建议，同级按维度权重排序，给出最值得先修的前 3 项

展示完即结束，不落盘任何文件。

## 硬性规则

- 只读：禁止修改任何文件；除只读查看外，禁止任何 git 状态修改操作。
- 权重与扣分值固定；问题必须逐条附证据。
- 老代码惯例 < 项目规范；两者冲突时一律以规范为准。
- 输出为评审结论，不直接动手改代码（用户另有要求除外）。
