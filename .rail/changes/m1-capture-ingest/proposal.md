# Proposal: M1 捕获与入库（m1-capture-ingest）

## 1. 背景与动机

拾光（ShiGuang）是一个本地优先的个人 AI 第二大脑项目（Electron + React + pnpm workspaces monorepo）。M0 骨架已完成，M1 是首个实质迭代「捕获与入库」。

用户明确的产品原则：**先健全信息收集能力，AI 全部后置**（M5 才开始分析流水线）。

当前状态：monorepo 三包（`apps/desktop`、`packages/ai`、`packages/shared`）的 src 目前均为空；`packages/ai` 已安装 better-sqlite3。M1 要交付的最小闭环是：用户在任何应用里选中内容 → 按全局热键 → 内容落库到本地 SQLite → 通过系统通知获得捕获结果反馈 → 借助通用 SQLite 工具查看数据。

M1 运行形态：无窗口后台运行，系统通知是唯一用户触点；仅在拾光运行期间热键可用（关窗/自启属 M3 REQ-APP-01，不在本次范围）。

## 2. 需求与范围

### 功能描述

构建拾光的捕获与入库能力：

1. 用户在任何应用里选中内容（文字或图片），按全局快捷键（默认 Cmd+Shift+C），被选中的内容保存到本地——不需要打开拾光窗口，不打断当前工作。
2. 每条记录带时间信息，关掉应用、重启电脑后已保存内容不丢。
3. 捕获成功后有简单明确的提示；所有失败场景（未选中、剪贴板为空、权限不足、保存失败等）都必须明确提示，不能静默。
4. 用户能在本地查看已保存的数据——借助现成通用工具（DB Browser for SQLite / TablePlus），不要求拾光自带查看界面（README 写清 db 位置并推荐工具）。
5. 首次使用缺少必要权限（macOS Accessibility）时，有清晰的引导，不能出现"按了没反应、不知道为什么"。
6. `pnpm dev` 一键起 + `.env` 模板（KIMI_API_KEY 占位即可，M1 不用 LLM）。

### 范围边界

**M1 做：**

- 全局快捷键捕获（默认 Cmd+Shift+C，M1 写死不可配置），捕获引擎位于 `apps/desktop` 主进程（README 决策 #1：捕获逻辑不独立成包，globalShortcut/clipboard 强依赖 Electron 主进程）。
- 文字捕获：按纯文本入库（富文本不保留格式）。
- 图片捕获：图片以文件形式存数据目录，库中存路径。
- 数据持久化：主进程经 `packages/ai` 的 DAO 层读写 better-sqlite3；单一 SQLite 文件（后续向量共存）。
- 捕获结果系统通知（成功与失败均提示）。
- macOS Accessibility 权限检测与首次引导。
- README 补充 db 文件位置与查看工具推荐。
- `.env` 模板 + `pnpm dev` 一键启动（REQ-DX-02）。

**M1 不做（明确排除）：**

- 查询界面（M2）。
- 圈屏/选区截图（M4）。
- AI 分析/LLM 调用（M5，`.env` 仅占位）。
- 托盘常驻、关窗后热键可用、开机自启（M3 REQ-APP-01）。
- 敏感内容防护/脱敏（M1 明文入库，见第 3 节已知风险）。
- 捕获热键可配置。
- React UI（本迭代不写任何渲染层界面）。

### 边缘场景处理（已对齐）

| 场景 | 处理方式 |
| --- | --- |
| 剪贴板为文件（Finder 复制的文件） | 提示"暂不支持该类型"，不入库 |
| 富文本（网页/Word 带格式文字） | 按纯文字存储（剪贴板中的纯文本版），格式不保留 |
| 图文并存（网页复制常见） | 合并为一条记录，文字为主、图片作为附件 |
| 重复捕获相同内容 | 照常入库，每次捕获是独立时间线事件 |
| 高频连按热键 | 每次都完整处理，不防抖 |
| 超长文字/超大图片 | 原样保存，不截断不压缩 |

### 约束

- 捕获引擎位于 `apps/desktop` 主进程（README 决策 #1），不独立成包。
- DB 访问层（DAO/schema/迁移）位于 `packages/ai`。
- **记录类型可扩展**：数据模型必须为未来类型（M4 选区截图等）留扩展口（节点 3 已确认纳入 M1 约束）。
- 不写 React UI；通知是唯一用户触点。

### 验收标准

任意应用选中文字/图片 → 按 Cmd+Shift+C → 看到成功通知 → 用 DB Browser for SQLite 打开 db 文件能看到这条记录；权限不足时有引导；所有失败场景（未选中/剪贴板为空/权限不足/保存失败/不支持的类型）均有明确提示，无静默失败。

## 3. 未来场景与扩展预判

- **记录类型扩展（M4 选区截图等）**：M1 数据模型必须预留类型扩展口。建议应对方向：records 表设计 `type` 字段 + 扩展字段（如 payload JSON 或附件关联表），避免 M4 时推倒重来。
- **敏感内容误捕获（密码/密钥）**：M1 不做防护，明文入库，属已知风险。建议应对方向：记入风险清单，M9 以脱敏配置解决；在此之前 README 需如实说明"数据明文存储"。
- **数据量增长后的查询性能**：M1 不设性能指标。建议应对方向：在 REQUIREMENTS.md 的 M2 章节记待办——M2 需处理分页/懒加载/搜索索引，避免数据量上来后查询卡顿。
- **向量数据共存**：README 架构已定位单一 SQLite 文件后续承载向量。建议应对方向：schema 迁移机制在 M1 一并建立（迁移框架本身属 M1 数据层职责），为后续扩展留好迁移通道。
