# Tasks 格式规范

本文件定义 `.rail/changes/<slug>/tasks.md` 的格式。

## 核心约定（机器解析锚点，必须刚性遵守）

1. **任务序号**：`任务 N`（1-based 连续编号）——caller 与 subagent 的定位锚。
2. **前置条件**（必需字段）：依赖的任务序号列表。无依赖写"无"，否则用 `[1]` / `[1, 3]` 格式——caller 据此构建排程依赖图。
3. **文件路径**：任务描述中的目标文件用反引号路径写出（如 `` `src/foo.ts` ``）——caller 据此做同文件并发控制。

## 结构示例（示例性质，非穷举）

```markdown
---
slug: <slug>
derived_from: .rail/changes/<slug>/design.md
---

# Tasks — <slug>

## 实现任务

- [ ] 任务 1：<自包含描述，见下方内容红线>
  - **前置条件**：无
  - **对应验收标准**：AC-1（推荐填写，仅供评审追溯）
  - **关键契约**（可选）：
    ```ts
    function example(param: Type): ReturnType
    ```

- [ ] 任务 2：...
  - **前置条件**：`[1]`
  - <自由说明 bullet：测试注意事项 / 用户选型记录 / 验证方式说明等>
```

多包/多仓变更可用 `### 子包名` 分节组织任务（任务序号仍全局连续）。

## 字段说明

- **对应验收标准**（推荐）：覆盖 design.md「验收标准」中的条目编号，1-3 个高度相关的 AC。仅供评审阶段追溯覆盖，code 阶段不消费。
- **前置条件**（必需）：见核心约定。
- **关键契约**（可选）：从 design.md「实现方案」摘录的接口/数据结构，确保实现不偏离设计。
- 任务条目下允许附加自由说明 bullet / 代码块（测试注意事项、用户选型、验证方式说明等），属条目的一部分，subagent 必须阅读并遵循。

## 内容红线

1. **描述自包含**：执行者仅凭本条目（含其字段与附加说明）即可完成并自验该任务；禁止引用 design.md 等其他文件段落作为完成依据。
2. **禁占位措辞**：TBD / 待补充 / "适当"处理 / "参考上文" / "类似任务 N"；精确值（文案、数值、函数签名、URL）直接写进描述。

## 任务粒度

每个任务必须同时满足：
1. **单一职责**：只实现 1 个函数/方法/组件/文件的一种行为。
2. **时间盒**：前置条件满足后，熟练开发者 5 分钟内完成。
3. **无子任务**：描述中不得出现"然后...""接着...""以及..."等串行动词。
4. **单文件优先**：尽量一个任务只改 1 个文件。
5. **测试文件不作为独立任务条目。**
