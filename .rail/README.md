# `.rail/` — Rail workflow state

This directory is created and maintained by the [Rail](https://github.com/) workflow inside OpenCode. It holds the runtime artifacts of the workflow:

```
.rail/
├── changes/
│   └── <slug>/                # change folder
│       ├── proposal.md        # produced by /rail-proposal (status also tracked in frontmatter)
│       ├── design.md            # produced by /rail-design
│       ├── tasks.md           # checkbox progress tracker (lives across stages)
│       ├── status             # single-line status file: pending-design → pending-code → in-progress → pending-docs → done
└── docs/                      # design decisions & tech debt, organized by domain
    ├── .index.md              # docs directory index
    └── <domain>/             # domain directory
        └── README.md          # design decisions & tech debt for this domain
```

`.rail/` (auto-generated by `/rail-evolve`):
```
.rail/
├── rules/                        # project rules extracted from completed changes
│   └── <domain>.md               # domain-scoped code rules
└── schemas/                       # reference docs (format specs, test quality)
    ├── design.schema.md
    ├── tasks.schema.md
    ├── proposal.schema.md
    ├── domain.template.md
    └── test-quality.md
```

## Quick Mode: `/rail-quick`

For small changes — bug fixes, minor adjustments, copy/style tweaks, single-file optimizations — you can use the **quick mode** instead of the full five-stage workflow:

```
/rail-quick <free-form request>
```

Quick mode is **zero-documentation**: no `proposal.md`, no `design.md`, no `tasks.md`, no `review.md`. The AI builds a lightweight `quick_design` in memory, dispatches the coder subagent directly, runs tests, and shows you the diff.

**When to use quick mode vs. full workflow:**

| Use `/rail-quick` | Use `/rail-proposal` → full workflow |
|---|---|
| Bug fixes with localized impact | New features |
| Single-file adjustments | Cross-module changes |
| Copy/style/config tweaks | Architecture changes |
| Performance micro-optimizations | Changes requiring design decisions |

If the AI detects the change is larger than expected (touches core files, spans multiple modules, requires new dependencies), it will **interrupt** and recommend the full workflow.

## Standalone tools

These commands are **not part of the workflow** — they can run at any time, on any scope:

- `/rail-ask <question>` — query project knowledge from `.rail/docs/` and the codebase.
- `/rail-code-review <scope>` — independent multi-dimension code review of the user-scoped code (files, directories, commit ranges, or working-tree changes). Reviews five dimensions — conventions, design, completeness, tests, security — and produces a weighted 100-point score with a graded issue list (severity, `file:line` evidence, fix direction). Nothing is written to disk.

## Lifecycle of a change folder

1. `/rail-proposal <free-form request>` creates `.rail/changes/<slug>/` after the user confirms the slug.
2. `/rail-design <slug>` fills in `design.md` and finalizes `tasks.md`.
3. `/rail-code <slug>` implements code and tests in the project source, checking off `tasks.md` items in the same commit as the code.
4. `/rail-review <slug>` is triggered automatically by `/rail-code` — the review subagent judges the diff against `design.md` and returns a verdict directly (no `review.md` file).
5. `/rail-docs <slug>` extracts design decisions and tech debt into `.rail/docs/<domain>/README.md` and updates `.index.md`, then writes the `status` file to `done`.
6. `/rail-evolve <slug>` (optional) analyzes the completed change for repeatable patterns and, with user confirmation, writes extracted skills to `.opencode/skills/`.

The workflow status is tracked in `.rail/changes/<slug>/status` (a single-line file). Each stage reads this file for entry validation and writes the next status on completion. The `proposal.md` frontmatter `status` field is retained as a human-readable reference but is not used by the workflow.

## What is human-editable

- `.rail/docs/**` — yes. This is the project's living record of design decisions and tech debt. Hand-edits are expected.
- `.opencode/skills/**` (non-`rail-*` prefixed) - yes. Auto-generated by `/rail-evolve` from completed changes. Hand-edits are expected as the project evolves.
- `.rail/schemas/**` - no. These are managed by `rail sync` and provide format specifications for subagents.
- `.rail/changes/<slug>/**` — no, by default. These files are the workflow's authoritative artifacts. If you must edit by hand, do it between stages, not during a subagent run. Workflow progress is tracked in the `status` file; the `proposal.md` frontmatter `status` field is a human-readable reference only.
